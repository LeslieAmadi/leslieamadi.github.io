Kestrel SDK: Android Quickstart

Integrate a rewarded-advertising SDK into an Android application: add the dependency, initialise once in the application lifecycle, preload an ad, handle callbacks that arrive off the main thread, retry transient failures, and grant the reward only when it has actually been earned.

Requirements

This quickstart integrates Kestrel into an Android application: initialise the SDK, preload a rewarded ad, display it on demand, and grant in-game currency when the user earns a reward.

Before you start, you need:

  • Android Studio, and an Android application written in Kotlin.
  • minSdk 23 or higher.
  • A Kestrel application ID from the developer dashboard.
  • An emulator or physical device for testing.

The example uses Kotlin 2.0.21 with a compatible Android Gradle Plugin and Gradle wrapper.

1. Add the dependency

In the project-level build.gradle.kts, declare the plugins:

build.gradle.kts (project)
plugins {
    id("com.android.application") version "8.7.3" apply false
    id("org.jetbrains.kotlin.android") version "2.0.21" apply false
}

In the app module's app/build.gradle.kts, apply them and add Kestrel:

app/build.gradle.kts
plugins {
    id("com.android.application")
    id("org.jetbrains.kotlin.android")
}

android {
    defaultConfig {
        minSdk = 23
    }
}

dependencies {
    implementation("com.kestrel.ads:kestrel-ads:1.0.0")
}

Sync the project with Gradle to resolve the dependency.

Expected result. The project recognises the Kestrel classes and compiles against them.

2. Configure the manifest

Open app/src/main/AndroidManifest.xml. Add the Internet permission outside the <application> element, then declare your application class and application ID:

AndroidManifest.xml
<uses-permission android:name="android.permission.INTERNET" />

<application
    android:name=".KestrelApplication"
    android:label="@string/app_name"
    android:theme="@style/Theme.MyApp">

    <meta-data
        android:name="com.kestrel.ads.APP_ID"
        android:value="YOUR_KESTREL_APP_ID" />

    <!-- Keep your existing activity declarations here. -->

</application>

Replace YOUR_KESTREL_APP_ID with the ID from your dashboard, and keep your existing launcher activity.

Do not embed server credentials. An application ID identifies your app and is safe to ship. Private keys and server secrets are not: values compiled into an APK can be extracted.

3. Initialise the SDK

Android does not run an app as a single program with a main(). The operating system creates and destroys components. The Application object is created once when the process starts. An Activity is one screen, and Android destroys and recreates it routinely, for example on rotation.

Kestrel initialises once per process, so it belongs in Application.onCreate().

KestrelApplication.kt
package com.example.myapp

import android.app.Application
import com.kestrel.ads.KestrelAds
import com.kestrel.ads.LogLevel

class KestrelApplication : Application() {

    override fun onCreate() {
        super.onCreate()

        KestrelAds.setLogLevel(LogLevel.DEBUG)
        KestrelAds.initialize(this)
    }
}

Set the log level before initialising, or initialisation itself produces no output. Disable debug logging in production builds.

Warning 1 — initialise once. Do not initialise Kestrel in Activity.onCreate(). Android recreates activities on configuration changes, so the SDK would initialise again on every rotation, registering duplicate listeners and repeating process-level setup.

4. Load and show a rewarded ad

Preload the ad when the screen opens so the user never waits for a network request after tapping. The flow is:

  1. Create a KestrelRewardedAd and register a listener.
  2. Request the ad. Keep the button disabled while it loads.
  3. Enable the button on onAdLoaded().
  4. Show the preloaded ad when the user taps.
  5. Grant the reward from onUserEarnedReward(), never from onAdClosed().
  6. Load the next ad after closure.
  7. Retry transient load failures with bounded exponential backoff.

Kestrel delivers callbacks on a background thread, so every UI update is posted to the main thread.

MainActivity.kt
package com.example.myapp

import android.os.Bundle
import android.os.Handler
import android.os.Looper
import android.widget.Button
import android.widget.TextView
import androidx.appcompat.app.AppCompatActivity
import com.kestrel.ads.KestrelRewardedAd
import com.kestrel.ads.RewardedAdListener

class MainActivity : AppCompatActivity() {

    private val mainHandler = Handler(Looper.getMainLooper())

    private lateinit var coinBalance: TextView
    private lateinit var watchAdButton: Button
    private lateinit var retryButton: Button

    private var coins = 0
    private var rewardedAd: KestrelRewardedAd? = null
    private var adReady = false

    private var retryCount = 0
    private var retryPending = false
    private val maxRetries = 3

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)

        coinBalance = findViewById(R.id.coinBalance)
        watchAdButton = findViewById(R.id.watchAdButton)
        retryButton = findViewById(R.id.retryButton)

        watchAdButton.isEnabled = false
        retryButton.visibility = Button.GONE

        watchAdButton.setOnClickListener { showRewardedAd() }
        retryButton.setOnClickListener {
            retryCount = 0
            retryButton.visibility = Button.GONE
            loadRewardedAd()
        }

        updateCoinBalance()
        loadRewardedAd()
    }

    private fun loadRewardedAd() {
        adReady = false
        watchAdButton.isEnabled = false

        val ad = KestrelRewardedAd()
        rewardedAd = ad

        ad.setListener(object : RewardedAdListener {

            override fun onAdLoaded() {
                mainHandler.post {
                    if (rewardedAd === ad) {
                        retryCount = 0
                        adReady = true
                        watchAdButton.isEnabled = true
                        retryButton.visibility = Button.GONE
                    }
                }
            }

            override fun onUserEarnedReward(rewardAmount: Int) {
                mainHandler.post {
                    coins += rewardAmount
                    updateCoinBalance()
                }
            }

            override fun onAdClosed() {
                mainHandler.post {
                    if (rewardedAd === ad) {
                        rewardedAd = null
                        adReady = false
                        loadRewardedAd()
                    }
                }
            }

            override fun onAdFailedToLoad(error: String) {
                mainHandler.post {
                    if (rewardedAd === ad) {
                        rewardedAd = null
                        adReady = false
                        watchAdButton.isEnabled = false
                        scheduleRetry()
                    }
                }
            }
        })

        ad.load()
    }

    private fun scheduleRetry() {
        if (retryPending) return

        if (retryCount >= maxRetries) {
            retryButton.visibility = Button.VISIBLE
            return
        }

        val delayMs = 2_000L * (1L shl retryCount)
        retryCount++
        retryPending = true

        mainHandler.postDelayed({
            retryPending = false
            loadRewardedAd()
        }, delayMs)
    }

    private fun showRewardedAd() {
        val ad = rewardedAd
        if (!adReady || ad == null) return

        adReady = false
        watchAdButton.isEnabled = false
        ad.show(this)
    }

    private fun updateCoinBalance() {
        coinBalance.text = "Coins: $coins"
    }

    override fun onDestroy() {
        mainHandler.removeCallbacksAndMessages(null)
        rewardedAd = null
        super.onDestroy()
    }
}

Three details in that listing are worth noticing. The rewardedAd === ad check means a late callback from a discarded instance cannot change the current state. Retries back off at two, four and eight seconds and stop after three attempts, revealing a manual retry button rather than leaving the user with a dead control. And onDestroy() clears pending callbacks so a scheduled retry cannot fire into a destroyed activity.

Warning 2 — respect callback threading. Android UI elements may only be touched on the main thread. Kestrel's callbacks arrive on a background thread, so every UI update goes through mainHandler.post(). Touching a view directly from a callback throws CalledFromWrongThreadException.

5. Grant the reward

Kestrel reports two separate events, and the difference between them matters commercially:

CallbackFires whenGrant the reward?
onUserEarnedReward()The user completed the eligible interaction.Yes
onAdClosed()The ad closed, whether completed or skipped.No
Warning 3 — never grant on ad closure. onAdClosed() fires whether the user watched the ad or quit after two seconds. Granting coins there teaches users to open an ad and immediately close it: the publisher pays out rewards nobody earned, and the advertiser is billed for impressions nobody saw.

The coins variable in the sample lives in memory on the device. A production rewards system should hold the authoritative balance on a trusted backend, verify the reward event server side where supported, and make reward processing idempotent so the same event cannot credit an account twice.

6. Test the integration

Run on an emulator or device using Kestrel's test mode and test ad units.

ScenarioExpected result
Application startsKestrel initialises once; debug logs appear.
Ad is loadingWatch Ad stays disabled.
Ad loadsWatch Ad becomes available.
User taps Watch AdThe preloaded ad displays with no wait.
User completes the adCoin balance increases by the reported amount.
User closes earlyNo reward is granted.
Load fails onceA retry is scheduled after two seconds.
Load fails four timesAutomatic retries stop; the manual retry button appears.
Device rotatesThe activity is recreated without reinitialising the SDK.
Activity is destroyed mid-retryNo pending callback fires into the destroyed activity.

Test the early-close case deliberately. An integration that grants rewards on closure looks identical to a correct one until someone notices the payout figures.

Watch Logcat for initialisation messages, load failures and callback events. Do not log credentials or user data.

Troubleshooting

SymptomLikely cause
Gradle cannot resolve the dependency Wrong coordinates, missing repository, or an incompatible Kotlin plugin, AGP and Gradle wrapper combination.
The ad never becomes available Wrong application ID, no network, or the load callback is not reaching the listener.
CalledFromWrongThreadException A view is being updated directly from a background callback. Post to the main thread.
The SDK initialises repeatedly Initialisation is in an activity rather than Application.onCreate().
Users get rewards after closing early Reward logic is in onAdClosed() instead of onUserEarnedReward().
No debug logs setLogLevel() runs after initialize(), or Logcat is filtered to another process.
Crash after leaving the screen A pending retry fired into a destroyed activity. Clear callbacks in onDestroy().

Writer's note

About this piece

Kestrel does not exist. I wrote this to work through how mobile SDK documentation differs from the server-to-server REST documentation I have written professionally: initialisation is tied to an operating-system lifecycle rather than to a request, callbacks arrive on threads the developer did not choose, and platform configuration lives in files outside the code.

The three warnings are the ones I would expect a real integration to get wrong. Initialising in an activity is invisible until something breaks under rotation. Touching a view from a background callback crashes immediately but only on the path that is hardest to test. Granting a reward on ad closure never crashes at all: it just quietly costs money, which is why it is the one in a red callout rather than a footnote.
